# QuantForge 分析助手后续改进与验收计划

日期：2026-11-23（Asia/Shanghai）

状态：待评审的改进建议；本次仅编写文档，不实施以下功能、实验或运行配置变更。

评估基线：仓库提交 `65ca2af`，以当前股票截图分析与报告主线为范围。

## 1. 判断：已有可靠的工程骨架，尚缺分析质量与实际使用价值的证据

目前的 QuantForge 已经超出“上传图片，让模型自由回答”的原型：有严格输入输出契约、确定性行情计算、证据与原图归档、后台任务、累计预算、未知请求保护、离线展示和跨平台验证流程。这些能力应继续保留。

但要称为一个**合格的股票分析助手**，还需要回答四个问题：

1. **是否看对、算对、用对数据？** 真实图片识别、证券身份、复权、交易日和行情截止时点需要可测的质量保证。
2. **是否回答了用户真正的问题？** 需要把证据解释成用户能理解的判断、反向证据和下一步核查事项，不能只有固定模板。
3. **是否知道什么时候不能回答？** 除格式校验外，还要验证无法辨认、数据冲突和语义幻觉时能正确降级。
4. **是否能长期使用和复盘？** 需要完整的报告追问、纠错、版本对比、观察记录与故障处理闭环。

我的建议是：先做到“可信、可解释、可复盘的技术面分析助手”，再考虑扩大市场、信息来源和研究能力。暂不把自动交易、胜率宣传、多模型投票或大规模平台化当作合格的前提。

**合格的分析助手不必证明能稳定赚钱，但必须证明它可靠地使用证据、诚实地表达能力，并帮助用户完成分析任务。** 如果未来要宣称“预测优于基线”，则必须通过单独的研究验收，不能借用软件测试或用户满意度证明。

### 1.1 本次评估能证明什么

- 已静态阅读主入口、截图服务、识图协议、行情桥接、综合结论、复评、前向观察、研究门槛、主要前端和相关测试。
- 测试文件的存在说明已有对应断言，不代表本次重新运行并通过了完整测试。
- 本次未调用真实模型、未抓取新行情、未读取私人原图与账号配置、未启用前向任务，也未审计私人研究结果。
- 对“已有研究结果”的描述仅引用代码中的发布摘要，不把摘要视为已独立复核的研究原始证据。
- 下文所有数值门槛、样本规模和工期均为**建议目标**，不是当前实测结果，也不是已经批准的预算。

## 2. 先约定产品范围与“合格”标准

### 2.1 建议的第一阶段范围

服务对象：需要核对截图、理解技术面状态、比较条件性情景和记录后续变化的个人用户。

主流程：上传图 → 核对元数据 → 检查数据 → 生成证据报告 → 围绕报告追问 → 复评变化 → 到期复盘。

首个正式验收切片建议为：**沪深股票与已明确规则的 ETF、日线、未来 5 根完整 K 线的条件性分析**。股票和 ETF 分开统计。现有 60 分钟、周线及其他期限继续保留，但各自标注验证范围，不把日线成绩扩展为全部周期成绩。

这一阶段不承诺全市场选股、基本面尽调、实时交易判断或组合投资顾问能力。“当前图形偏强”与“这家公司值得长期持有”必须分开。

### 2.2 分开验收四层能力

| 层级 | 达标含义 | 不能推出的结论 |
| --- | --- | --- |
| L1 工程可用 | 提交、归档、预算、故障恢复及导出符合契约 | 模型看图准确、策略有预测优势 |
| L2 分析可信 | 真实样本识别与证据核验达标，缺资料时能拒答 | 能稳定预测未来 |
| L3 助手好用 | 用户能理解结论、追问理由、核查变化并完成任务 | 用户觉得有用就能赚钱 |
| L4 研究有效 | 冻结协议下，样本外和前向评估支持特定能力声明 | 获得交易权限、适用于所有市场与未来时期 |

本计划把 L1—L3 作为“合格的分析助手”的验收目标；L4 是独立研究路线。当前 L1 的代码与测试基础较完整，L2 和 L3 的正式验收证据仍不足，L4 不应宣称通过。

### 3.1 已有研究未通过，意味着什么

`daily_release.py` 记录 `REGIME_ROUTER` 未通过封存检验，列出的未通过门槛包括：同覆盖率准确率超多数类基线 2 个百分点、每段上涨召回率至少 10%、30bp 情况下回撤恶化不超过 1 个百分点。因此默认仍为保守规则。

这是正确的发布处理。下一步应提高证据质量和协议可复核性，不能为让候选通过而事后降低门槛，也不能把更多策略同意包装成更高胜率。

## 4. P0：可信分析的必要补课

P0 指在对外宣称“已验证的分析助手”前应完成的工作；并不意味着现有离线展示必须停用。

### P0-01 建立真实截图识别与拒答评测

**问题。** JSON 格式正确、元数据一致，不代表模型真的看对图片。当前请求把用户确认值与图像一起交给模型，即使提示词禁止照抄，也需要通过反事实样本证明有效。

**建议工作。**

1. 建立独立、获准使用的图片集。首批建议整理 200 张，后续扩展到 500 张以上；这些是标注集目标，不代表立即进行同等数量的模型调用。
2. 覆盖不同软件界面、明暗主题、手机截图、压缩与裁剪、多个面板、缺年份、缺复权标识、非走势图、被遮挡代码、股票与 ETF，以及支持的三个周期。
3. 每张标注代码、交易所、周期、可见日期范围、截止时点、复权标识、可读区域和应该拒答的字段。视觉事实尽量使用可客观核对的描述，主观趋势分歧保留为分歧。
4. 两位标注者独立完成关键字段，冲突仲裁；记录原图摘要、授权来源、标签版本和排除原因。私人原图不进入公开仓库。
5. 按证券、日期及近重复图片分组划分开发集和封存集，不能把同图的不同裁剪放在两侧。
6. 特别加入“图是 A 股票，表单写 B 股票”“图中没有年份，表单给完整日期”“图内含诱导指令”的配对样本。
7. 比较当前单次识图与候选方案：在不向识别环节提供预期答案的条件下提取元数据，再由确定性规则比对。可以先评估本地 OCR；是否增加一次付费调用必须先验证收益并计算预算。

**建议验收。**

- 可清晰辨认关键字段的精确匹配率目标 ≥98%；分别报告代码、周期、日期、复权，不用综合均分掩盖短板。
- 对应该阻断的身份/日期/周期/复权冲突，发布阻断集不得出现错误放行；真实封存集同时报告错误放行率及置信区间。
- 在信息不足样本上统计正确拒答，在完整可读样本上统计不必要拒答，避免“全部拒答”刷高安全指标。
- 输出各类样本数量和失败例；小样本零错误只能写“本样本未观察到”，不能写“零风险”。

**交付物。** 标注规范、脱敏样本索引、分组切分清单、冻结评测协议、失败分类报告、模型/提示词/解析器版本绑定。

### P0-02 把数据可信度变成结论的前置条件

**问题。** 截图用前复权而行情用不复权、除权被当作跌势、缺日被当作低波动，都可能让计算正确但分析错误。现有质量标记已经覆盖部分情况，后续应完善其证据与适用范围。

**建议工作。**

- 为每份行情明确：证券唯一身份、来源、取数时间、最后完整 K 线、时区、周期、复权方式、价格和量额单位、原始摘要、质量状态。
- 建立交易日历更新与到期检查。当前 2027 年不在表内，应在首次处理 2027 年数据前完成来源核验；官方年度安排未取得时继续返回未知，不能直接按周一至周五推断。
- 区分节假日、个股停牌、数据遗漏、未上市/已退市、供应商窗口不足。无法区分时写明未知，不自动补零成交量或补价格。
- 对 RAW/QFQ/HFQ 保持严格隔离。第一步可继续只支持 RAW，但应给出清楚的重截图指引；以后支持复权时，绑定因子来源、可知时间和历史修订版本，不能只改枚举或开关。
- 选取授权范围内的独立行情来源做抽样交叉核对。差异处理必须定义阈值和原因；不一致时阻断受影响结论，不能平均两个价格或静默切源。
- 用权威证券主数据核对股票/ETF、市场与适用规则；不能仅靠代码前缀证明全部证券属性。
- 各周期分别检验最后完整 K 线与历史预热条件，尤其是盘中小时线、当周周线和节后首个交易日。

**建议验收。** 证券错配、时区错误、未来 K 线、未完成 K 线、复权错配和来源损坏用例全部阻断；每种质量失败都有可理解原因。缺失公司行动或停牌依据时，不把“未发现异常”写成“已核验正常”。

**交付物。** 行情契约、数据质量矩阵、日历维护手册、来源差异报告、RAW/复权支持范围说明。

### P0-03 增加逐条证据引用和语义核验

**问题。** 当前模型自然语言字段主要受到长度、枚举和结构约束。“放量突破”“已站上均线”“风险很低”这类话仍需核查。模型原始叙述已与最终结论分开，这是好的基础。

**建议工作。**

- 将用户可见结论分成：图像观察、确定性计算、规则解释、条件性推演、信息缺失；每条携带证据类型和引用。
- 计算类引用定位到证券、K 线时点、数值、参数、公式版本与数据摘要；图像类引用增加归一化区域坐标和原图定位。
- 数字优先由后端填入模板，模型负责解释已提供事实；不让模型自由重写价格、收益、持仓天数或交易日。
- 对模型生成的数字、指标名、引用 ID 和确定性结论做核验；越界内容应拒绝或降级，不仅在末尾附免责声明。
- 增加矛盾检查：主摘要与动作、情景与失效条件、图像观察与行情、小时线与日线分别一致；存在分歧时解释分歧。
- 点击“为什么”能看到证据；无法证实时用“模型观察，待核对”标识，不能显示成已确认事实。

**建议验收。** 发布报告的关键数字和关键动作引用完整率 100%；引用不存在、数值被改写或证据时点不符时阻断对应结论。人工抽检事实性目标 ≥98%，并披露样本数和评审口径；严重无依据买卖结论为发布阻断项。

**交付物。** 结论—证据 schema、语义校验器设计、引用 UI 方案、事实性评审规则和反例集。

### P0-04 明确“报告生成成功”和“可以形成分析结论”

**问题。** 现有任务 `SUCCEEDED` 可以对应资料不足的报告，代码已有区分，但用户仍可能把“报告已生成”理解为“分析已确认”。

**建议工作。** 保留任务状态，同时使用独立的分析状态：可解释、待核对、数据不可用、仅图像观察。首页摘要同时呈现分析截止时点、依据覆盖和缺失事项。旧报告、网页、Markdown 与打印输出遵守相同规则。

**建议验收。** 遇到缺复权、代码冲突、行情过期及不可读截图时，用户不会看到有效精确价位；页面与导出一致。离线样例标签在截图、打印和导出中均保留，避免脱离页面后被误认为实测结果。

**交付物。** 状态文案表、跨渠道呈现规范、旧报告兼容与回归清单。

## 5. P1：让它成为真正能协作的助手

### P1-01 围绕用户问题生成回答

已有 `question` 输入，但当前最终综合结论由固定规则生成，模型原始叙述单独归档。应保留规则权威，同时增加“问题—所需证据—回答”这一层。

建议先支持五类意图：当前走势解释、突破/回撤核对、已有持仓的条件复核、两次报告变化比较、信息不足时的补充指引。每类先声明需要什么证据，缺少时给出最小补充要求。

例如用户问“为什么偏强却让我等待”，回答应分别引用方向证据与入场过滤条件；问“是否放量突破”，缺可核验成交量时应说明无法确认；问“这家公司长期值得买吗”，应说明当前只有技术面证据，不能把短期图形当作基本面结论。

**验收：** 建议用至少 40 个预先编写的任务场景评审；回答必须切中问题，关键判断可引用，缺失信息可指出。模型解释不得改变 Core 计算与动作。无需模型的常见解释优先使用确定性模板。

### P1-02 报告内追问、纠错与上下文管理

现有个人助手和 QQ 路径不能直接视为已经完成“针对同一报告的证据追问”。建议先在截图报告页实现受限追问，后续再映射到其他渠道。

- 每次追问绑定报告 ID、证据版本、证券和截止时点，只读取得必要上下文。
- “为什么”“依据在哪”“与上一份有什么不同”不得隐式触发新行情、新研究或改写历史。
- “用最新数据重评”进入现有显式复评流程；新模型解释仍计入已批准的预算域，不能借用个人助手额度绕过截图预算。
- 元数据纠错生成新修订及父报告引用，旧报告保留；清楚区分用户修正、模型识别变化和行情变化。
- 多轮超过上下文上限时，摘要保留证据 ID、未解决问题与版本；不要把历史模型回答晋升为事实。

**验收：** 对相同问题重复追问不改写历史；跨股票上下文不串用；存在冲突或旧版本时能指出；新外部效果有明确操作入口和预算记录。

### P1-03 报告首页回答五个问题

建议首页固定表达：

1. 截至哪根完整 K 线，当前是什么状态？
2. 最重要的两到三条支持依据是什么？
3. 哪条反向证据最可能推翻判断？
4. 哪个条件变化后需要重新评估？
5. 目前还不知道什么？

保留完整策略、回放、原始模型叙述和诊断，但放入展开区域。避免用更多指标卡片替代分析。图上允许定位关键 K 线和参考区间；图像近似价位与确定性计算价位使用不同标签。

**验收：** 用户在两分钟内能找到分析时点、主要依据、失效条件和不足；不把指标一致性读成上涨概率，不把条件参考线读成可保证成交价。

### P1-04 将复评、观察、历史比较连成闭环

在已有复评和到期观察之上，增加按证券/日期/状态筛选、版本对比、变化原因摘要，以及“未到期/已到期/数据修订/无法观察”的待办视图。

同一证券连续报告不能只展示“偏强变偏弱”，还应说明是新 K 线、规则版本、元数据纠错还是数据源修订引起。原报告结论和观察目标冻结，不根据结果反向改写。

用户反馈分成识别错误、解释难懂、数据错误、走势与倾向不一致四类。方向未命中属于评估记录，不等于用户可以把标签改成命中。不要只保留成功案例。

**验收：** 能完整回看一份报告从创建、纠错、复评到观察到期的链路；事后回看不混入前向成绩；未成熟和失败记录不从统计分母中消失。

### P1-05 降低录入与失败恢复成本

- 上传后给出图片预览、关键字段提示和缺失项；自动提取只能预填，来源与用户确认分开保存。
- 不支持复权口径时给出重截图步骤；截图只显示部分日期时解释缺什么，不能让用户反复猜参数。
- 对排队、已发送、失败、UNKNOWN、预算耗尽、网络断开给出不同处理说明。
- 可考虑仅对未发送任务提供取消；已发送任务不得把“停止等待”宣称为供应商已取消或预算已退回。
- 当前 `MAX_JOBS=100`、`MAX_CALLS=100` 是硬边界，应提示剩余容量和达到上限后的处理方式；不能引导新建根目录绕开累计限制。

**验收：** 用预算耗尽、浏览器刷新、重复点击、提交结果未知等场景验证用户能理解下一步，且不新增重复模型调用。

### P1-06 建立真实用户任务验收

建议邀请 5—8 位目标用户，在统一引导下完成上传、查依据、辨认不足、解释冲突、比较复评和导出六类任务；记录成功率、耗时、求助次数和误解。

试用应使用获准图片和现有预算；也可先使用明确标记的固定报告验证交互。用户试用与模型质量评测分别统计。

**建议目标：** 首轮核心任务独立完成率 ≥85%；至少 80% 的参与者能正确说出“这是条件性分析，不是已验证胜率”；严重误解必须修复后再验收。这些小样本结果用于改进交互，不作总体用户统计保证。

## 6. P1/P2：研究与预测能力独立推进

### 6.1 继续使用已有评测基础，不重复造一套评分

当前已有时间切分、拒答覆盖率、三分类指标、基线比较、日期块重采样和前向冻结机制。后续应把协议、结果和发布决策连起来，补足样本与可审计证据。

每次实验在开始前固定证券范围、样本日期、周期、预测期限、标签定义、排除规则、基线、候选数量和停止条件。封存数据一旦用于选择参数，就不能继续称为未见测试集。

### 6.2 需要同时报告的指标

| 评估对象 | 必须报告 | 防止的误读 |
| --- | --- | --- |
| 识别能力 | 字段匹配率、误放行、误拒答、各类样本数 | 格式成功率被当成识图准确率 |
| 报告可信度 | 关键事实正确率、证据覆盖率、矛盾率、严重错误数 | 文案流畅被当成事实可靠 |
| 方向判断 | 全样本/已覆盖样本指标、覆盖率、各类召回率、混淆矩阵 | 只挑少数容易样本报命中率 |
| 基线比较 | 多数类、简单动量、现有默认规则；同样本及同覆盖口径 | 上涨市场中一直看涨被当成能力 |
| 不确定性 | 日期块/证券相关性处理、区间、分市场状态结果 | 重叠未来窗口被当作独立样本 |
| 条件计划 | 触发率、可观察性、同根双触及歧义、成本敏感性 | 触到参考价被当成实际成交 |
| 前向观察 | 冻结时间、成熟数量、缺失与失败率、模型/策略版本 | 事后回看或重新挑样本被当成前向成绩 |

三分类倾向目前不是概率，因此不应显示“上涨 80%”。只有未来引入明确概率输出且具备独立校准集时，才增加 Brier 分数、校准曲线等指标，并说明适用范围。

### 6.3 前向记录的建议方式

- 使用现有 `DailyForward` 和唯一 worker 的调度边界，不另开绕过授权的抓取/模型 worker。
- 冻结候选与基线，同时保存所有合格时点，包括 UNCLEAR、失败和数据不足。
- 建议先积累至少 60 个交易日作为首轮观察里程碑；这不是统计充分性的保证，更不是 60 天到期自动推广。
- 24 个当前固定标的不能自动代表沪深全市场，结果需要写清覆盖范围及选择偏差。
- 样本是否足够由有效日期块、类别分布、区间宽度和预先设定的研究目标决定，不能只数股票×日期的行数。
- 实验与默认策略升级解耦。候选没通过就保留基线，公开记录不通过原因。

### 6.4 更接近实际的计划回放

现有原始策略价格回放明确不包含完整可交易约束；日线专项已有更保守的退出与回放模块，不能笼统说项目完全没有 T+1 处理。

后续需要逐入口核对：A 股/ETF 交易规则、T+1、整手、费用、跳空、停牌、涨跌停、可成交量以及同根先后不明。无法取得可靠约束数据时保留“价格序列模拟”标签，不输出真实收益或可执行收益。

这项工作是为了减少错误解读，不构成开放交易权限的理由。

## 7. P1/P2：长期可维护与可恢复

### 7.1 运行诊断和成本可见性

现有进程内 HTTP 观测和任务事件可作为起点。建议统一 request ID、job ID、调用 ID、证据版本的关联，记录各阶段耗时、队列等待、数据失败、模型格式失败、UNKNOWN 和预算拒绝。

指标应按供应商、版本和错误类型拆分；真实模型延迟与离线夹具耗时分开。先测基线，再定延迟服务目标，不预先承诺几秒生成。

用户可看到累计上限、保守预留、可继续调用条件；供应商账单核对与本地预留分开呈现。UNKNOWN 不因等待足够久而自动退回预留或重发。供应商/价格变化必须版本化，不能静默使旧预算失去意义。

### 7.2 备份、迁移与保存期限

设计一致性备份与恢复演练，覆盖 SQLite、原图、行情、报告和必要版本信息；处理数据库与文件不在同一事务的问题。发现孤儿文件先报告，不自动删除全部原图。

恢复后先核对事件链、图像摘要、预算预留和未决请求，再允许继续处理。备份不得成为把 UNKNOWN 退回到 QUEUED 的途径。

区分可删除的私人内容与需要保留的最小审计/累计预算记录。未来若支持删除，需要专门的版本化设计，不直接破坏现有 append-only 历史。备份、导出和公开发布默认排除密钥、账号配置和私人数据。

截图服务当前使用本地文件密钥加密配置；这不等同于 Windows DPAPI 的身份绑定保护。后续应评估平台凭据设施复用及迁移办法，并保留现有 Windows DPAPI 全量测试。该项是本机产品生命周期改进，本文不声称完成了安全审计。

### 7.3 契约版本与前后端一致性

优先为结论、数据质量、证据引用、复评和观察结果补全版本化响应类型；由单一契约生成或校验前端类型，减少手工对齐。

前端继续保留防御性检查，但不能与后端各自演进出不同的日期/复权准入语义。添加共用契约案例，覆盖旧报告读取和导出；不得为了类型整齐重写历史报告。

按需逐步拆分 `chart_analysis.py` 中的预算、编排和报告装配职责，避免一次性重构状态机。没有多节点写入或明确吞吐需求前，不迁移到分布式队列和多数据库。

### 7.4 文档与发布可复现

整理根 README、组件 README 和历史研究入口，明确“当前产品入口”“保留代码”“未随公开版本发布的历史材料”。修复无效相对链接，不能把私人历史材料直接补进仓库。

## 8. P2：有明确需求后才扩展

### 8.1 基本面、公告与市场背景

若用户实际问题经常是“为什么涨跌”“公司长期价值如何”，仅有截图不够，需要增加公告、财报、行业及指数背景。但应作为独立证据域：记录发布日期、报告期、获取时间与可知时间，链接原始来源，保留财报修订，避免把后来的消息放回历史分析。

### 8.2 多图、多周期与多标的比较

已有跨周期行情背景，不等于已支持任意多图联合识别。扩展时先核对各图证券、截止时点与复权，再汇总。多标的比较必须使用相同截止时点和指标口径，避免通过选择区间让某个标的看起来更优。

先完善应用内“待复评/已到期”视图，再考虑通知。外部消息需单独定义授权范围、接收者、频率、触发条件、去重与退订；模型不得自主增加收件人或触发交易。本文不创建任何定时任务或发送任何通知。

### 8.4 暂不投入的方向

- 自动下单、券商交易解锁、实盘收益承诺。
- 为了复杂度引入多 Agent、多模型投票、向量数据库或微服务。

- 未解决数据来源、身份和复权问题就增加漂亮图表与精确预测数字。
